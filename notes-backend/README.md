# Notes Backend (v3.0)

Cloudflare Workers + D1 (SQLite) + R2 (object storage) backend for the
**Notes** Android app. Provides email/password auth, note sync, and image
uploads.

- Runtime: Cloudflare Workers (V8, ES modules, Web Crypto)
- Storage: D1 (relational), R2 (images)
- Auth: JWT (HS256), PBKDF2 / SHA-256 password hashing
- Types: TypeScript strict

## Setup

### 1. Install dependencies

```bash
cd notes-backend
npm install
```

### 2. Log in to Cloudflare

```bash
npx wrangler login
```

### 3. Create the D1 database

```bash
npx wrangler d1 create notes-db
```

Copy the printed `database_id` into `wrangler.toml`:

```toml
[[d1_databases]]
binding = "DB"
database_name = "notes-db"
database_id = "REPLACE_WITH_REAL_ID"   # ← paste here
```

### 4. Create the R2 bucket

```bash
npx wrangler r2 bucket create notes-images
```

### 5. Generate a JWT secret and put it in `wrangler.toml`

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

```toml
[vars]
JWT_SECRET = "REPLACE_WITH_RANDOM_32_CHARS"   # ← paste here
ENV = "development"
```

### 6. Run migrations locally

```bash
npm run db:migrate
# equivalent to: wrangler d1 migrations apply notes-db --local
```

### 7. Run the dev server

```bash
npm run dev
# equivalent to: wrangler dev
```

### 8. Apply migrations to remote + deploy

```bash
npm run db:migrate:remote
npm run deploy
```

## API

All requests and responses are JSON unless noted. All responses include CORS
headers (`Access-Control-Allow-Origin: *`). Errors come back as
`{ "error": "..." }` with an appropriate HTTP status.

### Authentication

Most endpoints require an `Authorization: Bearer <token>` header. The token is
issued by `/auth/register` and `/auth/login` and is valid for **30 days**.

#### `POST /auth/register`

```bash
curl -X POST https://<your-worker>.workers.dev/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"hunter2hunter2"}'
```

Response 200:
```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user": { "id": 1, "email": "alice@example.com", "created_at": 1730000000000 }
}
```

#### `POST /auth/login`

```bash
curl -X POST https://<your-worker>.workers.dev/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"hunter2hunter2"}'
```

Response: same shape as register.

#### `GET /auth/me`

```bash
curl https://<your-worker>.workers.dev/auth/me \
  -H "Authorization: Bearer <token>"
```

Response 200:
```json
{ "user": { "id": 1, "email": "alice@example.com", "created_at": 1730000000000 } }
```

### Notes

All note endpoints require authentication.

A note id is a **UUID string** generated by the Android client. The server
treats it as the primary key, so the mobile app is free to assign ids and
sync them up.

#### `GET /notes?since=<timestamp_ms>`

Optional `since` query parameter (epoch milliseconds). Returns all notes for
the authenticated user with `updated_at > since`. If `since` is omitted,
returns every note.

```bash
curl "https://<your-worker>.workers.dev/notes?since=1730000000000" \
  -H "Authorization: Bearer <token>"
```

Response 200:
```json
{
  "notes": [
    {
      "id": "f6c5...",
      "user_id": 1,
      "title": "Shopping list",
      "content": "Milk\nEggs",
      "created_at": 1730000000000,
      "updated_at": 1730000010000,
      "is_favorite": 0,
      "is_trashed": 0,
      "background_color": 0
    }
  ],
  "sync_timestamp": 1730000020000
}
```

#### `GET /notes/:id`

```bash
curl https://<your-worker>.workers.dev/notes/f6c5... -H "Authorization: Bearer <token>"
```

#### `POST /notes`  (create **or** update)

Upsert. The mobile app typically pushes every locally-changed note to this
endpoint after each edit.

```bash
curl -X POST https://<your-worker>.workers.dev/notes \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{
    "id": "f6c5a8b1-1234-5678-9abc-def012345678",
    "title": "Shopping list",
    "content": "Milk\nEggs",
    "is_favorite": 0,
    "is_trashed": 0,
    "background_color": 0,
    "created_at": 1730000000000,
    "updated_at": 1730000010000
  }'
```

Response 200: the saved note.

#### `DELETE /notes/:id`

```bash
curl -X DELETE https://<your-worker>.workers.dev/notes/f6c5... \
  -H "Authorization: Bearer <token>"
```

Response 200:
```json
{ "deleted": "f6c5..." }
```

> Trash is a local-only concept in v3.0; this is a hard delete.

### Image uploads

#### `POST /upload`  (authenticated)

JSON body, base64-encoded file:

```bash
curl -X POST https://<your-worker>.workers.dev/upload \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{
    "filename": "cat.jpg",
    "content_type": "image/jpeg",
    "data": "<base64-encoded bytes>"
  }'
```

Response 200:
```json
{
  "id": "3c2f...",
  "url": "https://<your-worker>.workers.dev/files/uploads/1/3c2f.../cat.jpg",
  "r2_key": "uploads/1/3c2f.../cat.jpg",
  "content_type": "image/jpeg",
  "size": 124532
}
```

#### `GET /files/<r2_key>`  (public)

Direct, cache-friendly access to an uploaded image:

```
https://<your-worker>.workers.dev/files/uploads/1/3c2f.../cat.jpg
```

## Auth flow

1. App calls `POST /auth/register` (or `/auth/login`) with `{email, password}`.
2. Server returns `{token, user}`.
3. App stores the token (e.g. EncryptedSharedPreferences).
4. App sends `Authorization: Bearer <token>` on every subsequent request.
5. Server verifies the JWT (HS256, signed with `JWT_SECRET`), looks up the
   user, and scopes all queries by `user_id`.

Password storage: PBKDF2 / SHA-256 / 100,000 iterations, 16-byte random salt,
32-byte key. Stored as `salt:hash` (both halves hex-encoded).

---

## Note sync flow

The mobile app keeps its local Room database as the source of truth and
treats the server as a sync target. The typical flow is:

1. After a local insert/update, POST the note to `/notes` with the client-side
   UUID and the client-side `created_at` / `updated_at`.
2. Server upserts. If the row already exists, the server keeps
   `updated_at = MAX(local, remote)` so a slow client cannot regress the
   timestamp.
3. On launch (and on demand), the app calls `GET /notes?since=<last_sync_ms>`
   to pull only what changed.
4. Trash is local-only in v3.0; deleted notes are hard-deleted on the server.

---

## Image upload flow

1. App encodes the image bytes as base64.
2. App calls `POST /upload` with `{filename, content_type, data}`.
3. Server validates the content type is `image/*`, generates a UUID, stores
   the bytes in R2 at `uploads/<user_id>/<uuid>/<filename>`, and returns a
   public `url` of the form `<base>/files/<r2_key>`.
4. The app embeds this URL in the note's content and persists the note locally
   (and via `POST /notes`).

## CORS

All responses include:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

Preflight (`OPTIONS`) requests return `204 No Content` with the headers above.
You do not need any extra CORS configuration on the Android side — the
default OkHttp / Retrofit setup just sends the headers through.

## Security notes

- `JWT_SECRET` must be a long random string (≥ 32 bytes). Changing it
  invalidates all existing tokens.
- `database_id` in `wrangler.toml` must match the id returned by
  `wrangler d1 create`.
- `notes-images` is the R2 bucket name; it must exist before deploying.
- `/files/*` is intentionally **public** so the mobile app can render images
  directly. If you need private images, swap `serveFile` for signed URLs.
- All passwords are stored as `salt:pbkdf2-sha256-100k-hex`, never in plain
  text. PBKDF2 is implemented with Web Crypto, not Node's `crypto` module,
  because this code runs on the Workers V8 isolate.

## Local development tips

- `wrangler dev` exposes a local D1 and a local R2 (Miniflare-backed).
- Use `wrangler d1 execute notes-db --local --command 'SELECT * FROM notes;'`
  to poke around local D1.
- Use `wrangler r2 object put notes-images/foo --file=foo.png` to seed local
  R2 if needed.
- Hot-reload works for most code changes; `wrangler dev` will restart on
  changes to `wrangler.toml` or `migrations/`.
